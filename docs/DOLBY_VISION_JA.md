# Dolby Vision

tsMuxeR は、デュアルレイヤーの Dolby Vision ディスクを1つの Matroska ファイルに収め、そのファイルからディスクを再び構築できます。このページでは、各オプションが何をするのか、そして何が保持され、何が保持されないのかを説明します。

2.18 まで更新しています。

## デュアルレイヤーの Dolby Vision ディスクはどのような姿をしているか

この種のディスクは、映像を**2つの**ビデオストリームに分けて記録しています:

- **ベースレイヤー**。フル解像度の映像で、中身は通常の HDR10 です。
- **エンハンスメントレイヤー**。4分の1解像度のストリームで、Dolby Vision のデータを、1ピクチャにつき1つの RPU とともに運びます。

どちらも必要です。Dolby Vision を理解するプレーヤーは両者を組み合わせて読み取り、理解しないプレーヤーはベースレイヤーを HDR10 として表示します。

Matroska には、この種の2本目のビデオストリームを収める場所がありません。ビデオトラックが2つあるファイルはプレーヤーが想定しているものではなく、そこから Dolby Vision を有効にするプレーヤーは存在しません。そこで tsMuxeR は、全体を**1つの**トラックに収めます。ベースレイヤー、Dolby Vision を何も知らないデコーダーが読み飛ばせるように包んだエンハンスメントレイヤー、そして RPU です。再エンコードは一切行わず、並び順も一切変えません。

## ディスクを Matroska として保存する

ディスク、またはその2つのビデオストリームを追加し、**MKV多重化**を選んで多重化します。2つのビデオストリームは1つの映像の2つのレイヤーとして認識され、自動的に結合されます。

## ディスクを再び構築する

Matroska ファイルを開きます。結合された Dolby Vision トラックは**2行**として一覧に表示され、一方に `(base layer)`、もう一方に `(enhancement layer)` と付きます。両方を選択し、Blu-ray出力を選んで多重化します。レイヤーは再び分離され、それぞれ正しいストリームに配置されます。

コマンドラインでは、同じことを `subTrack=` を使った2行で記述します:

```
V_MPEGH/ISO/HEVC, "film.mkv", track=1, subTrack=1, fps=23.976
V_MPEGH/ISO/HEVC, "film.mkv", track=1, subTrack=2, fps=23.976
```

`subTrack=1` がベースレイヤー、`subTrack=2` がエンハンスメントレイヤーです。

## Dolby Vision のプロファイル

デュアルレイヤーディスクは**プロファイル 7** です。多くの機器は、同じディスクであれば問題なく再生するにもかかわらず、ファイルからのプロファイル 7 は受け付けません。**プロファイル 8.1** はシングルレイヤーの形式で、はるかに多くの機器が受け付け、受け付けない機器では HDR10 にフォールバックします。

ソースがデュアルレイヤーの Dolby Vision ディスクで、出力が Matroska の場合、出力形式の横に **Dolby Vision** の選択欄が表示されます:

| 選択肢 | 動作 |
|---|---|
| プロファイル 7（ディスクと同じ） | ディスクの内容をそのまま収めます。これが既定です。 |
| プロファイル 8.1（より多くの機器で再生可能） | メタデータを変換し、ファイルがシングルレイヤーの Dolby Vision として再生されるようにします |

コマンドラインでは `--dv-profile=7` または `--dv-profile=8.1` にあたります。

### プロファイル 8.1 にしてもファイルは小さくなりません

ここが意外に思われる点です。ディスクをプロファイル 8.1 に変換する一般的な方法はエンハンスメントレイヤーを捨てるもので、容量の節約はそこから生まれています。

tsMuxeR はこれを捨てません。エンハンスメントレイヤーはトラックの中を一緒に運ばれ、その傍らにディスク**本来の** Dolby Vision メタデータが添付されるため、元のディスクを寸分たがわず再構築できます。したがって変換後のファイルはプロファイル 7 のものとほぼ同じ大きさで、わずかに大きくなることもあります。

小さなプロファイル 8.1 のファイルが欲しく、ディスクの再構築はどうでもよいという場合、このツールはその用途には向きません。

### なぜ元のメタデータを保持しなければならないのか

プロファイル 7 のメタデータを 8.1 に変換する処理は**多対一**です。異なる元データが同じ結果になります。プレス製造された市販ディスクで計測したところ、変換後のメタデータの3分の2は区別のつかないものになり、多いところでは91通りの異なる元データが1つの結果に収束しました。これをあとから元に戻すことは、実装の出来がどれほど良くても不可能です。

そのため、元データは復元するのではなく、そのままの形で保持しています。ディスクからファイルへ、そして再びディスクへという往復が成り立つのはこのおかげであり、ファイルが小さくならないのもこれが理由です。

### プロファイル 8.1 に必要なもの

プロファイル 8.1 は **libdovi** ライブラリを使用します。これは tsMuxeR の一部ではありません。

| プラットフォーム | 対応方法 |
|---|---|
| Windows 64ビット | `dovi.dll` を `tsMuxeR.exe` と同じ場所に置きます。ビルド済みのものが公開されています。 |
| Linux、macOS | libdovi をソースからビルドするか、お使いのディストリビューションにパッケージがあればそれをインストールします |
| Windows 32ビット | 利用できません。このライブラリに32ビットのビルドは存在しません。 |

**入手先。** このライブラリは [dovi_tool のリリースページ](https://github.com/quietvoid/dovi_tool/releases) で
`libdovi-<バージョン>-x86_64-pc-windows-msvc.zip` として公開されています。この書庫に入っている
ファイルは `dovi.dll` の一つだけで、それを `tsMuxeR.exe` と同じ場所に置きます。

同じページにある `dovi_tool-<バージョン>-x86_64-pc-windows-msvc.zip` は取らないでください。
これはコマンドライン ツールであり、tsMuxeR では使えません。両者は並んで置かれており、
ツールのほうが分かりやすい名前なので、これがよくある間違いです。

リリース番号は dovi_tool のものなので、中のライブラリは別の番号になります。`libdovi-3.4.0` は
リリース `2.3.3` に添付されています。ライブラリのバージョン番号でページを探しても見つかりません。
3.3.1 以降の libdovi であれば、tsMuxeR が必要とする4つのエントリ ポイントを備えています。

ライブラリが見つからない場合、`--dv-profile=8.1` は多重化が始まる**前に**、その旨のメッセージとともに拒否されます。機能の処理が途中まで進んでから失敗することはありません。

## 保持されるもの

計測は短いクリップではなくタイトル全体で行っています。クリップではストリームの終端やセグメント同士のつなぎ目を検証できず、そのどちらも重要であることが分かったためです:

- 本編1本まるごと、73 GB、両レイヤー: 再構築したストリームはディスクと**バイト単位で同一**でした。ベースレイヤー 59.33 GB、エンハンスメントレイヤー 4.25 GB で、どちら側にも余りはありません。ディスク本来の 166,928 件のメタデータレコードもすべて復元されました。プロファイル 7 でもプロファイル 8.1 でも同じで、つまりメタデータを変換して戻しながら、ディスクはそのまま正確に返ってきます
- **シームレスブランチング**のタイトル1本まるごと、22か所でつないだ23個のクリップ: プロファイル 7 で再構築したものと、プロファイル 8.1 で再構築したものが、両レイヤーともバイト単位で同一でした

平たく言えば: **出てくるディスクは、入れたディスクそのものです。**

### スタートコードの形式がどう保たれるか

ディスクはスタートコードを3バイトか4バイトのどちらかで書きます。どちらも規格上正当でデコード結果も同一ですが、1枚のディスクの中では一貫しています。そして Matroska はこの映像を長さ接頭辞付きで格納するため、スタートコードをまったく含みません。そのため Matroska から再構築したディスクは、ソースが何であれ常に4バイトで出てきており、短い形式を使うディスクは、ほかがどれだけ正確でもバイト単位で戻ってくることがありませんでした。

いまはソース自身の形式がファイルとともに運ばれ、再現されます。記録は NAL タイプごとに行います。ディスクが実際にそうしているからであり、一律に3バイトとするのは規格に適合しないからです。1つのソース内で両方の形式が現れる NAL タイプは、推測せずに何も記録しません。全体を通して4バイトだったソースも同様で、それは tsMuxeR がもともと書き出す形式だからです。したがって、特筆すべきことのないファイルには余計なものが付かず、最悪の場合でも従来どおりの動作であって、誤った動作にはなりません。これは Dolby Vision に固有の話ではありません。ふつうのシングルレイヤーのディスクを Matroska にして戻す場合も、同じ仕組みで形式が保たれます。

### ディスクのそれ以外の部分

上記の記述は映像についてのものです。音声、字幕、そしてディスク構造は、ほかのどの多重化とも同じく新たにオーサリングされますが、これらも推測ではなく計測しました。同じディスクを2通りの経路で、レイヤーから直接、そして Matroska ファイル経由でオーサリングした結果です:

| | 結果 |
| --- | --- |
| ロスレス音声 | バイト単位で同一 |
| その隣にある AC-3 コア | 1フレーム分だけ短い。下記参照 |
| 字幕 | バイト単位で同一 |
| クリップ情報ファイル、シークマップも含む | バイト単位で同一 |
| プレイリスト、インデックス、ムービーオブジェクト | バイト単位で同一 |
| プログラムマップとクロックリファレンス | すべてのフィールドが同一 |
| トランスポートストリームの配置 | 切り出しの最後の一瞬を除いて同一 |

**唯一の傷:** Matroska ファイルからディスクをオーサリングすると、AC-3 互換コアの最後のフレームが失われます。これはロスレスストリームをデコードできないプレーヤーのために存在する代替ストリームの 32 ms 分です。ロスレスストリーム自体は完全で、同一です。これは新しい問題でも Dolby Vision に固有の問題でもありません。2本の音声ストリームを1本に織り直す箇所で起こり、最後のコアフレームに寄り添うロスレスフレームがもう残っていないためです。

### 推測ではなく拒否

保持されているメタデータがファイルの申告内容と一致しない場合、そのファイルは何かが書き出される前に**拒否されます**。一見正しく見えて実際には誤っているディスクを作ってしまわないためです。これは、切り出されたり、再多重化されたり、ほかのツールで添付ファイルを取り除かれたりしたファイルにも当てはまります。

tsMuxeR が書き出したファイルを、添付ファイルを落としてしまう別のソフトウェアでコピーした場合、ディスクの再構築に必要な Dolby Vision データは失われています。元のファイルを保管しておいてください。

## シングルレイヤーの Dolby Vision ファイル

すでにシングルレイヤーであるファイル、つまりプロファイル 5 やプロファイル 8 のファイルには、分離すべきエンハンスメントレイヤーがありません。分割を指示すると、空の2本目のトラックを作る代わりに、説明とともに拒否されます。代わりに1つのトラックとして多重化してください。
